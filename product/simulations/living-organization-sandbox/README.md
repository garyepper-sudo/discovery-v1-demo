# Living Organization Sandbox Foundation

This Product-owned, non-Production simulation uses organization `sandbox-northstar-implementation-services-001`, a bounded company derived from Northstar material without modifying Northstar benchmark fixtures. Its primary Question is “Why are customer implementations taking longer?” The unrelated control area is community science volunteering.

The six ordered manifest batches contain company context, an incomplete operating picture, diagnostic comparisons, a policy constraint and counterevidence, future Outcome/Learning source material, and five negative controls. All files are Markdown, source-controlled, content-hashed, and loaded locally. No single source states a complete conclusion.

The replay calls the canonical organization-investigation orchestration, which owns Evidence production, cognition, Runtime evolution, persistence, and history. An exact eligible sandbox disclosure decision feeds the canonical Organizational Understanding projection compiler. Checkpoints contain bounded identities, counts, digests, uncertainty, contradiction, investigation, and evolution summaries; they never serialize raw Runtime or source text.

Reset owns exactly three artifacts beneath an explicitly named temporary sandbox root: the dedicated Runtime file, checkpoint file, and reset receipt. It rejects Production, the wrong organization, repository/shared paths, path aliases, and symbolic roots or owned subdirectories. It never mutates Drive content. Future sandbox-owned artifact classes must register exact filenames in the manifest rather than broaden deletion.

Commands:

- `npm run validate:living-organization-sandbox-manifest`
- `npm run living-organization-sandbox:reset`
- `npm run living-organization-sandbox:replay -- batch-2`
- `npm run living-organization-sandbox:replay-all`
- `npm run validate:living-organization-sandbox-foundation`

Commands default to an isolated temporary root. A persistent local root requires `--root=/tmp/discovery-living-organization-sandbox-<name>` and remains subject to the same fail-closed checks.

This foundation proves deterministic local corpus identity, bounded reset, canonical local replay, authorized projection, longitudinal checkpoints, negative controls, and exact cleanup.

## Google Drive acceptance

The same corpus can be transported through the existing governed Google Drive connector in development or sandbox mode. `googleDriveCorpus.ts` adds only a strict sandbox binding and acceptance result; OAuth, encrypted credentials, exact-folder authorization, retrieval, extraction, source versioning, and synchronization receipts remain owned by `product/connectors/google-drive`.

The exact organization `sandbox-northstar-implementation-services-001` is eligible only for this Living Organization Google Drive acceptance purpose. The server-only `DISCOVERY_GOOGLE_DRIVE_SANDBOX_ACCEPTANCE_ENABLED=true` flag and exact `DISCOVERY_GOOGLE_DRIVE_SANDBOX_ACCEPTANCE_USER_ID` are both required in a fully validated local development environment with Clerk test keys. The default is disabled. Production, ordinary onboarding, unrelated connector purposes, arbitrary `sandbox-*` IDs, and non-exact users remain rejected. OAuth state, source, connected folder, Runtime, verification, and synchronization must retain the same exact organization; aliases and cross-organization mapping are prohibited.

Start this one OAuth flow with `purpose=living-organization-sandbox-acceptance`. Existing canonical `onb-dev-<24 hex>` connector behavior is unchanged.

The folder must be one exact configured, non-root, non-recursive folder. Supported acceptance MIME types are `text/plain`, `text/markdown`, and native Google Docs exported as text. A binding uses the logical manifest identity, logical version, normalized-content digest, Drive file and revision identities, retrieval time, manifest effective date, and exact authorization scope. A filename is never sufficient by itself.

Upload Batch 0 and Batch 1 first, then add Batches 2, 3, 4, and the negative controls in manifest order. Strict acceptance rejects unexpected files, digest mismatches, unsupported MIME types, missing documents, broad scope, cross-organization access, more than 32 files, or more than 2 MiB of extracted corpus content. An unchanged synchronization remains read-only and is compared with the local replay using transport-independent checkpoints.

The five-stage manual acceptance uses `batch-1`, `batch-2`, `batch-3`, `negative`, then `negative` again for the unchanged retry. The terminal fourth synchronization must use `negative`, because that existing manifest stage includes both Batch 4 and all five negative controls; `batch-4` is not the complete terminal corpus. The fifth synchronization repeats `negative` unchanged. Run each stage with `npm run google-drive:sync-sandbox-corpus -- --user-id <development-user> --organization-id sandbox-northstar-implementation-services-001 --source-id <connected-source> --through-batch <stage>`. It requires the existing development-only `.env.local` connector configuration plus `DISCOVERY_SANDBOX_GOOGLE_DRIVE_CONNECTED_FOLDER_ID` and `DISCOVERY_SANDBOX_GOOGLE_DRIVE_FOLDER_ID`. Live retrieval and extraction are staged in memory, strict sandbox scope/inventory/digest/MIME/count/byte validation completes before connector metadata is published, and only then does canonical sandbox replay proceed. It emits only the bounded local diagnostic receipt and never prints either configured folder value.

Development OAuth authorization codes, state, tokens, authorization headers, and session headers are never loggable, including after one-time code redemption. The canonical development launcher sanitizes framework stdout, stderr, split chunks, bounded line buffers, and shutdown output, the callback redirects successful authorization to a query-clean result route, and live-acceptance receipts use the same recursive redaction owner.

Semantic parity distinguishes canonical fields from documented transport-only fields. Drive file IDs, Drive revision tokens, connector request IDs, OAuth identity, retrieval timestamps, temporary paths, and Google account metadata remain in transport lineage but are excluded from the semantic checkpoint. Logical document identity/version, preserved passage content (represented only by safe digest and length), normalized content digest, effective date, Evidence disposition and identity, Understanding identity/revision, retained history, material change, contradiction, uncertainty, investigation opportunities, unrelated controls, and checkpoint construction remain binding. A parity failure returns a bounded field-level diff containing only safe values or digests; raw passage content is never emitted.

The first live Sync 1 exposed a normalization-seam mismatch and stopped before Batch 2: Drive extraction preserved the five documents apart from terminal newlines and produced the expected normalized digests, but metadata reload replaced preserved extracted text with digest-normalized lowercase/whitespace-collapsed text before canonical processing. Metadata reload now preserves extracted text while continuing to derive content-addressed identity from the existing normalized digest owner. A subsequent reviewed live rerun proved Sync 1 at five files, then exposed a cumulative Sync 2 divergence after the two Batch 2 files were added. Passage content and normalized identity still matched; the earliest mismatch appeared in Evidence admission and propagated through Understanding identity/revisions, Runtime evolution history, contradictions, and checkpoint construction. The cause was oracle Runtime isolation: the canonical Runtime store resolves its directory at module import, while the replay attempted to redirect it afterward, allowing both expected and observed replays to share retained process Runtime. Each acceptance replay now runs in a fresh process with its exact temporary Runtime directory established before canonical Runtime modules load. The comparator remains strict, admission order remains semantic, and deterministic two-stage validation proves a genuinely cumulative Batch 1 → Batch 2 sequence, equivalent post-Sync1 state, and no semantic mutation from the five unchanged files. Live acceptance remains incomplete; the live folder remains at seven files and zero subfolders, Batches 3–4 remain pending, and no Drive writes or Production access occurred during correction.
